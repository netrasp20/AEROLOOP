# Bootloader Identity Investigation — ArduPilot / QGroundControl

**Scope:** source-only architecture research. No Pixhawk commands, no bootloader entry, no UI changes, no resolver changes.

**Sources (exact revisions):**
- ArduPilot `Copter-4.7.0` — `Tools/AP_Bootloader/{bl_protocol.cpp,AP_Bootloader.cpp,board_types.txt}`, `libraries/AP_HAL_ChibiOS/hwdef/scripts/chibios_hwdef.py`, `libraries/AP_HAL_ChibiOS/hwdef/fmuv3/hwdef-bl.dat`, `hwdef/Pixhawk1/hwdef-bl.dat`, `hwdef/Pixhawk1-1M/hwdef-bl.dat`, `libraries/GCS_MAVLink/GCS_Common.cpp`
- QGroundControl commit `128517c23557c39b4694381d2a8860b818904137` — `src/Vehicle/VehicleSetup/{Bootloader,PX4FirmwareUpgradeThread,FirmwareUpgradeController,FirmwareImage}.cc`
- Official manifest `https://firmware.ardupilot.org/manifest.json.gz` (895 Copter images / 315 platforms at time of analysis)

---

## 1. Outcome

**Outcome C, exactly as scoped: bootloader identity alone still needs one more corroborating signal** — with one important refinement proven from source:

- **Bootloader identity is necessary and never sufficient** for board ID 9 (FMUv2/FMUv3/Cube F4).
- For the **2 MB vs 1 MB flash split**, bootloader flash size *is* sufficient (QGC rewrites ID 9 → 255 on flash-size evidence).
- For the **board-name split inside FMUv3** (Pixhawk1 vs Pixhawk1-1M vs Cube F4 vs XUAV), the third signal is **the USB product string read from bootloader mode**, matched against manifest `bootloader_str`. In ArduPilot `Copter-4.7.0` this string is generated by `chibios_hwdef.py` as `"%BOARD%-BL"` for bootloader builds.
- `info_manifest` `image_size` is **not** consulted by QGC for board selection at all (it is read, then used only for `.px4` decompression). It is therefore **not** part of the minimum QGC-equivalent identity.

**QGC-equivalent minimum identity tuple:**

| # | Field | Source | Role in QGC |
|---|-------|--------|-------------|
| 1 | Bootloader protocol version (`INFO_BL_REV`) | `PROTO_GET_DEVICE=0x22`, arg `0` | Range gate; flash-size correction threshold |
| 2 | Bootloader board ID (`INFO_BOARD_ID`) | arg `2` | **Primary** manifest filter (`board_id`) |
| 3 | Bootloader flash size (`INFO_FLASH_SIZE`) | arg `4` | Rewrites ID 9→255; skips `fmuv2` rows |
| 4 | USB product string in bootloader mode | USB descriptors | Substring match vs manifest `bootloader_str` → picks best index |

Not part of QGC selection: `INFO_BOARD_REV` (arg 3), `INFO_VEC_AREA` (arg 5), `USB serial`, MCU chip description, OTP. QGC reads none of these for selection. **Forcing these into the minimum would be a YantraYug policy choice, not a QGC requirement** — and adding stricter checks could reject images QGC accepts.

## 2. Normal mode vs bootloader mode

| Signal | Normal mode (current Pixhawk) | Bootloader mode | Independent physical evidence? |
|--------|------------------------------|-----------------|-------------------------------|
| USB VID:PID | `1209:5741` (`4617/22337`) | Same IDs; ArduPilot reuses FMUv3 IDs for BL | No — same for all FMUv3-class |
| USB product | `Pixhawk1` | `%BOARD%-BL` | **No — generated from firmware build** |
| USB manufacturer | `ArduPilot` | `ArduPilot` | Vendor only |
| USB serial | `3C0027000951363033383531` | bootloader descriptor | No manifest mapping |
| `AUTOPILOT_VERSION.board_version` | `0x00090000` → ID 9 | n/a (MAVLink absent) | No — `APJ_BOARD_ID << 16` |
| `BRD_TYPE` | `2` | n/a | **No — writable parameter** |
| `BRD_SERIAL_NUM` | `0` | n/a | **No — user-defined parameter** |
| `uid` (MAVLink) | `0x0` | n/a | No |
| `INFO_BL_REV` | unavailable | available | Yes (bootloader binary) |
| `INFO_BOARD_ID` | unavailable (only via `board_version`) | available | Yes (bootloader build) |
| `INFO_FLASH_SIZE` | unavailable | available | **Yes — hardware flash geometry** |
| Bootloader USB product | unavailable | available | Derived from bootloader hwdef, but reflects *which bootloader binary is installed*, not the flash chip |

**Consequence:** entering bootloader mode changes the evidence class (physical flash geometry appears) but the USB product string is still hwdef-derived, not a factory readback.

## 4. QGC architecture (traced)

**Discovery / labelling** — `PX4FirmwareUpgradeThreadWorker::_findBoardOnce()`
- Tracks a target by `systemLocation`, falling back to captured USB **serial number** to follow re-enumeration to a different `/dev/ttyACM*`.
- Uses `QGCSerialPortInfo::getBoardInfo(boardType, boardName)` from **USB descriptors** — this is display/labelling only (`_boardTypeName`).
- Fast-path: if the descriptor already contains `"BL"` or `"Bootloader"`, skips the unplug/replug wait and handshakes immediately.
- Safety: ports already present at click time are recorded in `_ignoredPorts` so the `canFlash()` fallback cannot hijack an unrelated flashable device.

**Bootloader query** — `Bootloader::getBoardInfo()`
- Opens at **115200 8N1, no flow control**.
- `_sync()`, then `INFO_BL_REV` (range-gated by `BL_REV_MIN..BL_REV_MAX`), `INFO_BOARD_ID`, `INFO_FLASH_SIZE`.
- Correction: `if (boardID == boardIDPX4FMUV2 && bootloaderVersion >= _bootloaderVersionV2CorrectFlash && flashSize > _flashSizeSmall) boardID = boardIDPX4FMUV3;`
  — older v2 boards have silicon errata on large flash; v5+ bootloaders report it correctly.

**Selection** — `FirmwareUpgradeController::_buildAPMFirmwareNames()`
```cpp
rawBoardId = (_bootloaderBoardID == boardIDPX4FMUV3) ? boardIDPX4FMUV2 : _bootloaderBoardID;
for each manifest row:
    if (buildType == selected && chibios == apj && vehicleType == selected && boardId == rawBoardId) {
        if (row.fmuv2 && _bootloaderBoardID == boardIDPX4FMUV3) skip;   // excludes 2MB-only rows on 2MB+flash board
        else match, and if (bootloaderMatch && bestIndex == -1 && row.bootloader_str.contains(boardDescription))
            bestIndex = currentIndex;
    }
if (bestIndex == -1 && names.length() > 1) prepend "Choose board type";
```
- `fmuv2` is derived as `platform.contains("fmuv2")` — a **manifest platform-name heuristic**, not a hardware read.
- If no `bootloader_str` contains the USB description, QGC **presents the ambiguous list** rather than guessing. `USBID` is parsed into VID/PID arrays but **is not used in this selection path**.
- Board ID is folded one way only: 255 → 9 for manifest lookup, then `fmuv2` rows are filtered out. Manifest rows with board ID 255 are never selected.

**Image-level validation** — `FirmwareImage::isCompatible()`
- `.px4` header `board_id` vs device board ID; only rule: exact match, or `boardID==255` accepts `firmwareId==9`.
- `image_size` is read and used **only** for decompression. No size-based selection.
- `.apj` is passed through without a board-ID header check.

## 5. ArduPilot findings

- `AP_Bootloader` device info exposes bootloader revision, board ID, board revision, firmware size, vector area (`Tools/AP_Bootloader/bl_protocol.cpp`).
- `AP_Bootloader.cpp` initializes board type from `APJ_BOARD_ID` (a preprocessor define from hwdef) and computes firmware size from flash geometry.
- **`Tools/AP_Bootloader/board_types.txt` maps PX4 FMU v2, PX4 FMU v3, and Cube F4 all to board ID 9** — the collision QGC works around.
- **`hwdef/fmuv3/hwdef-bl.dat`** (`APJ_BOARD_ID TARGET_HW_CUBE_F4`, `FLASH_SIZE_KB 2048`) is included by **both** `hwdef/Pixhawk1/hwdef-bl.dat` and `hwdef/Pixhawk1-1M/hwdef-bl.dat`. Consequences in `Copter-4.7.0`:
  - bootloader board ID is 9 for all three,
  - bootloader-reported flash is 2048 KB for all three,
  - **the bootloader binary is the same for 2 MB and 1 MB Pixhawk1**, so flash size and board ID cannot distinguish `Pixhawk1` from `Pixhawk1-1M`.
- `chibios_hwdef.py::write_USB_config` sets `default_product = "%BOARD%"`, appending `"-BL"` when `is_bootloader_fw()`. Therefore the bootloader-mode product string is the board name plus `-BL` — the string manifest `bootloader_str` values such as `Pixhawk1-BL`, `Pixhawk1-1M-BL`, and `PX4 BL FMU v2.x` are matched against.
- `GCS_Common.cpp` builds `AUTOPILOT_VERSION.board_version = APJ_BOARD_ID << 16`, confirming the normal-mode `0x00090000` decode.

## 6. Requirements for a future YantraYug implementation

**Must have:**
1. Dedicated bootloader client implementing `PROTO_GET_DEVICE` (0x22) at 115200 8N1, read-only. No erase/program/reboot path in the identity component.
2. Explicit mode acquisition: user-driven reboot to bootloader, then **re-enumeration** — the device path and PID change. Must follow the board by USB serial number across the reenumeration, as QGC does.
3. Strict handshake-only flow. Any `sync`/query on a device that is actually running MAVLink risks being interpreted as MAVLink garbage; refuse to proceed if sync fails and the port still looks like a normal link.
4. Identity = (BL_REV, BOARD_ID, FLASH_SIZE) + bootloader USB product string, resolved against manifest `board_id` and `bootloader_str`.
5. Copy QGC's ID 9 → 255 flash-size correction **and** the `fmuv2`-row exclusion together; applying only one produces wrong results (either false 1 MB matches or 2 MB-only images offered to a small-flash board).
6. On no-`bootloader_str` match with multiple survivors, **return ambiguous**. Do not rank by version recency or URL order.
7. Manifest rows with board ID 255 are unreachable in this design, matching QGC.

**Must not have:**
- Any automatic bootloader entry, reboot, erase, or program action.
- Any use of normal-mode `BRD_TYPE`, `BRD_SERIAL_NUM`, or `USB serial` as identity input.
- Any assumption that bootloader USB product string is a factory measurement of the physical board.

**Safety note:** the real Pixhawk must not be used to validate this. Bootloader mode requires a reboot and a protocol handshake; the current hardware is explicitly out of scope. Validation must use the synthetic fixture only.

## 7. Open questions

- `bootloader_str` contains `PX4 BL FMU v2.x` for many platforms. QGC's `contains()` is directional (manifest string contains USB description), so a board whose USB description is `PX4 BL FMU v2.x` matches many rows equally and the first row wins as "best" — a latent QGC weakness worth *not* copying. Recommend requiring a unique match, else ambiguous.
- Whether `board_types.txt` collapsing Cube F4 into ID 9 also affects `TARGET_HW_CUBE_F4` in newer ArduPilot branches was not checked; only `Copter-4.7.0` was analysed.
- `.apj` images bypass QGC's board-ID header check entirely. If YantraYug wants stronger guarantees than QGC, `.apj` board identity must come from the manifest row selected, not from the file.
